# 任务：为整个实验代码仓库建立通用实验数据采集、性能计时与结果导出框架

## 一、任务背景与目标

请在当前代码仓库中设计并实现一套通用的实验数据采集与性能分析框架（Experiment Instrumentation Framework）。

该框架将用于当前所有算法实验，以及未来新增的实验。

当前仓库涉及或计划涉及的技术包括但不限于：

- CDC 分块算法：Rabin、BSW、TTTD、TTTD-S、FastCDC 等。
- 特征提取与相似性检测：Finesse SF、N-transform、文件级 SF 等。
- 精确去重与近似匹配。
- Chunk 索引及候选检索。
- Delta 编码：Xdelta 及未来可能加入的其他编码器。
- Raw / Delta 数据存储。
- 文件恢复与完整性验证。
- 其他未来新增的压缩、去重及数据处理算法。

本任务的核心不是修改或优化这些算法，而是建立一套独立、可扩展、低侵入性的统计基础设施，使所有算法能够使用统一的接口记录实验数据。

最终要求：

**无论运行哪一种算法，实验结束后都能够自动导出结构化数据，明确回答算法处理了多少数据、执行了多少次操作、各阶段耗时多少、资源消耗多少、最终存储效果如何，以及结果是否正确。**

后续新增算法时，不应重新开发一套统计系统，只需要接入现有框架并注册必要的专用指标。

## 二、开发前的代码审查要求

在修改代码之前，必须完整阅读当前仓库中与实验处理有关的源代码。

重点检查：

1. 所有算法的入口函数及调用关系。
2. 文件读取与数据生命周期。
3. CDC 分块及 Chunk 数据结构。
4. 指纹计算及精确去重。
5. 特征提取、候选检索和索引维护。
6. Delta 编码及其调用方式。
7. Raw / Delta 数据写入方式。
8. 文件恢复与校验流程。
9. 多线程及并行处理情况。
10. 当前已有的实验统计、日志及数据导出功能。

必须根据实际源代码确定埋点位置。

不得根据 README、函数名称或推测的流程直接设计埋点。

在正式修改前，先形成一份简短的实施方案，说明：

- 当前实际处理流程。
- 可以复用的已有代码。
- 需要增加的统计模块。
- 各阶段对应的真实函数及埋点位置。
- 当前代码中无法直接采集的指标。
- 可能影响性能或数据生命周期的风险。

完成审查后再实施。

## 三、总体架构设计

采用三层统计架构。

### 第一层：通用实验基础设施

提供所有算法共用的基础功能：

- 实验配置管理。
- 唯一实验 ID。
- 文件 ID、Chunk ID、Operation ID。
- 统一计时器。
- 计数器。
- 数据量统计。
- 内存及资源统计。
- 多线程统计聚合。
- 数据导出。
- 实验结果完整性检查。

### 第二层：通用处理阶段

根据算法实际执行情况，采集以下阶段：

- 文件读取。
- CDC 分块。
- 指纹计算。
- 精确去重。
- 特征提取。
- 索引构建。
- 候选检索。
- 相似性匹配。
- 数据编码。
- 数据压缩。
- 数据存储。
- 索引更新。
- 文件恢复。
- 完整性验证。

并非所有算法都需要执行全部阶段。

### 第三层：算法专用扩展

允许各算法注册自己的专用统计指标。

例如：

Finesse：
- Feature 提取。
- Super-Feature 构造。
- SF 槽位命中。
- FirstFit 行为。
- 候选 Chunk 数量。
- Delta 接受率。

N-transform：
- 特征构造。
- Super-Feature 生成。
- SF 匹配情况。
- 候选匹配分布。

FastCDC：
- Rolling Hash 计算。
- Normalization。
- Boundary Detection。
- 分块边界分布。

文件级 SF 预筛选：
- 文件级 Feature 提取。
- 文件级 SF 检索。
- 文件级候选数量。
- 相似度。
- 预筛选决策。
- 预筛选带来的计算节省。

以上仅作为示例，不得将框架限制在这些算法中。

新增算法应能够通过注册扩展指标的方式接入。

## 四、统一计时规范

### 4.1 计时工具

统一使用：

`std::chrono::steady_clock`

内部统一使用微秒（us）记录，导出时同时提供微秒和毫秒。

禁止使用可能受到系统时间调整影响的计时方式。

建议提供 RAII 计时器，例如：

- ScopedTimer。
- StageTimer。
- OperationTimer。

计时器必须支持：

- 自动开始与结束。
- 异常退出时正确结束计时。
- 累计耗时。
- 调用次数。
- 平均耗时。
- 最小耗时。
- 最大耗时。
- P50、P95、P99 延迟（适用时）。

### 4.2 三种时间必须区分

**Stage Time：阶段耗时**

记录某个阶段的累计执行时间。

**Operation Time：操作耗时**

记录某个具体操作的单次执行时间及分布。

**Wall-clock Time：实际经过时间**

记录整个实验从开始到结束的实际时间。

不得混淆三种时间。

尤其在多线程情况下：

- 不同线程的累计 Stage Time 可能大于 Wall-clock Time。
- 嵌套计时器可能发生时间重叠。
- 不允许简单相加所有阶段耗时并将其作为总运行时间。

必须明确区分串行时间、并行累计时间和端到端墙钟时间。

### 4.3 计时节点

所有实际执行的处理阶段均应有独立计时。

建议统一采用以下命名：

`file_read_time_us`

`cdc_total_time_us`

`fingerprint_time_us`

`dedup_total_time_us`

`feature_extraction_time_us`

`index_lookup_time_us`

`candidate_search_time_us`

`encoding_time_us`

`storage_write_time_us`

`recovery_total_time_us`

`verification_time_us`

实际字段应根据现有代码确定，可以扩展，但不得随意改变已有字段的含义。

### 4.4 计时开销控制

详细操作计时可能影响性能。

必须采用低开销设计：

- 优先使用线程本地计数器。
- 避免每次操作都写文件。
- 明细数据采用批量缓存和批量导出。
- 避免在高频操作中进行不必要的内存分配。
- 允许对单次延迟分布进行采样。
- 即使采样，也必须完整记录操作总次数和累计耗时。

必须通过基准测试评估统计模块自身的性能开销。

## 五、通用数据采集指标

以下指标构成所有实验共用的基础字段。

### 5.1 实验环境与配置

记录：

- experiment_id。
- 实验开始和结束时间。
- 算法名称及版本。
- 算法参数。
- Git Commit。
- 编译器及版本。
- 编译优化等级。
- 操作系统及版本。
- CPU 型号。
- 内存容量。
- 线程数量。
- 数据集名称及版本。
- 数据集文件数量。
- 数据集总大小。
- 实验运行模式。

所有实验必须保存完整配置，保证可复现。

### 5.2 文件级指标

每个文件记录：

- file_id。
- 文件名称。
- 文件类型。
- 文件大小。
- 文件 SHA-256。
- 文件读取耗时。
- 文件处理耗时。
- Chunk 数量。
- 唯一 Chunk 数量。
- 重复 Chunk 数量。
- 文件最终存储大小。
- 文件恢复耗时。
- 文件恢复正确性。

### 5.3 Chunk 级指标

每个 Chunk 尽可能记录：

- chunk_id。
- file_id。
- Chunk 在原文件中的偏移量。
- Chunk 大小。
- Chunk 指纹。
- 是否重复。
- 是否唯一。
- 是否参与后续处理。
- 所属算法。
- 最终存储类型。
- 实际存储大小。

算法专用字段可以扩展。

### 5.4 通用操作级指标

对关键操作记录：

- operation_id。
- operation_type。
- algorithm。
- file_id。
- chunk_id。
- start_time（可选）。
- duration_us。
- operation_result。
- 相关输入大小。
- 相关输出大小。

避免为每个低价值操作生成过多明细。

应根据分析价值选择需要记录的操作。

### 5.5 阶段级指标

每个阶段记录：

- stage_name。
- call_count。
- total_time_us。
- average_time_us。
- min_time_us。
- max_time_us。
- p50_time_us。
- p95_time_us。
- p99_time_us。

统计结果需要支持全局、文件级及算法级聚合。

### 5.6 索引指标

适用于存在索引结构的算法。

记录：

- 索引类型。
- 索引条目数量。
- 查询次数。
- 查询命中次数。
- 查询未命中次数。
- 插入次数。
- 删除次数。
- 查询耗时。
- 插入耗时。
- 索引构建耗时。
- 索引内存占用。

必须区分实际内存测量与估算内存占用。

### 5.7 缓存指标

适用于使用缓存的算法。

记录：

- 缓存容量。
- 当前占用。
- 请求次数。
- 命中次数。
- 未命中次数。
- 淘汰次数。
- 缓存命中率。
- 缓存读取耗时。
- 缓存写入耗时。

没有使用缓存的算法不生成这些指标。

### 5.8 存储指标

记录：

- Raw 数据字节数。
- Delta 数据字节数。
- 压缩数据字节数。
- 元数据字节数。
- 索引字节数。
- 临时文件字节数。
- 最终物理存储字节数。
- 实际写入次数。
- 存储耗时。

必须区分：

- 原始逻辑数据大小。
- 编码后的逻辑数据大小。
- 最终持久化物理存储大小。

不能用 Chunk 数量或理论数据大小替代真实存储占用。

### 5.9 恢复与正确性指标

记录：

- 恢复文件数量。
- 恢复 Chunk 数量。
- Raw 数据读取次数。
- 编码数据解码次数。
- 文件重组耗时。
- 完整性验证耗时。
- 恢复失败次数。
- SHA-256 验证通过次数。
- SHA-256 验证失败次数。

恢复正确性必须通过原始文件与恢复文件的 SHA-256 比对验证。

## 六、算法专用统计接口

需要设计一个通用的扩展机制。

例如：

```cpp
registerCounter("sf_lookup_count");
registerCounter("sf_hit_count");

registerTimer("sf_extraction_time");
registerTimer("delta_encoding_time");

registerMetric("candidate_count");
registerMetric("delta_size");
```

以上仅为接口示意，实际 API 应根据现有项目语言标准、代码风格和架构设计。

要求：

1. 专用指标必须注册到对应算法。
2. 必须提供指标名称、类型、单位和含义。
3. 不同算法可以注册不同指标。
4. 不得强制不具备某种操作的算法生成对应指标。
5. 指标名称不得冲突。
6. 导出时必须标明指标所属算法。
7. 支持未来增加新的指标而不修改已有 CSV 的基础字段定义。

如果某个算法没有执行某项操作，使用 N/A 或缺失值，不得填写 0。

## 七、实验运行模式

必须支持至少两种运行模式。

### 7.1 Benchmark Mode

性能基准模式。

目标：尽可能准确地比较不同算法的实际运行性能。

记录：

- 端到端运行时间。
- 阶段累计耗时。
- 操作调用次数。
- 文件及 Chunk 数量。
- 存储结果。
- 内存峰值。
- 正确性结果。

尽可能关闭高频操作明细记录。

### 7.2 Profiling Mode

详细分析模式。

目标：研究算法内部行为，定位性能瓶颈。

在 Benchmark Mode 的基础上，增加：

- Chunk 级操作明细。
- 候选检索明细。
- 算法专用匹配结果。
- 单次 Delta 编码耗时。
- 索引查询明细。
- 必要的资源变化记录。

两种模式必须采用相同的算法配置及输入数据，保证结果可比较。

## 八、数据导出要求

每次实验结束后自动创建独立目录。

建议采用以下目录结构：

```text
experiment_results/
└── experiment_YYYYMMDD_HHMMSS/
    ├── experiment_config.json
    ├── summary.json
    ├── file_metrics.csv
    ├── chunk_metrics.csv
    ├── operation_metrics.csv
    ├── stage_timing.csv
    ├── index_metrics.csv
    ├── cache_metrics.csv
    ├── storage_metrics.csv
    ├── recovery_metrics.csv
    ├── system_metrics.csv
    └── algorithm_metrics.jsonl
```

如果某类数据没有实际产生，可以不生成对应文件，并在实验清单中明确说明。

### 8.1 experiment_config.json

保存实验环境、算法配置、数据集信息、Git Commit、编译参数和运行模式。

### 8.2 summary.json

保存整个实验的汇总信息：

- 总文件数。
- 总输入字节数。
- 总 Chunk 数。
- 唯一 Chunk 数。
- 重复 Chunk 数。
- 总处理时间。
- 各阶段累计耗时。
- 端到端吞吐量。
- 最终存储大小。
- 总体存储压缩率。
- 峰值内存。
- 恢复正确率。
- 实验是否完整。

### 8.3 file_metrics.csv

一行代表一个文件。

保存文件基础信息、各阶段耗时、Chunk 统计、最终存储结果及恢复结果。

### 8.4 chunk_metrics.csv

一行代表一个 Chunk。

保存 Chunk 的大小、位置、指纹、去重情况、算法处理结果和最终存储类型。

### 8.5 operation_metrics.csv

一行代表一次被选定的具体操作。

保存操作类型、算法、关联文件、关联 Chunk、耗时、结果及输入输出大小。

### 8.6 stage_timing.csv

一行代表一个处理阶段。

保存调用次数、累计耗时、平均耗时、最小值、最大值和延迟分位数。

### 8.7 index_metrics.csv

保存索引构建、查询、插入、删除及内存占用数据。

### 8.8 cache_metrics.csv

保存缓存容量、命中、未命中、淘汰和读取耗时。

### 8.9 storage_metrics.csv

保存 Raw、编码数据、元数据、索引和物理存储构成。

### 8.10 recovery_metrics.csv

保存文件恢复耗时、解码情况和 SHA-256 验证结果。

### 8.11 system_metrics.csv

保存 CPU 使用率、内存峰值、线程数量及其他能够可靠采集的系统资源指标。

### 8.12 algorithm_metrics.jsonl

用于存储不同算法的专用扩展指标。

每行一个 JSON 对象，至少包含：

- experiment_id。
- algorithm。
- entity_type。
- entity_id。
- metric_name。
- metric_type。
- metric_value。
- unit。

不得将算法专用字段强行塞入通用 CSV 的固定列中。

## 九、统一评价指标

框架应提供基础的结果计算能力，但必须保留原始数据。

### 9.1 存储效果

至少提供：

- 原始数据大小。
- 最终存储大小。
- 存储压缩比。
- 空间节省率。
- 各类存储数据占比。

### 9.2 性能效果

至少提供：

- 端到端耗时。
- 各阶段耗时。
- 平均文件处理时间。
- 平均 Chunk 处理时间。
- 输入吞吐量。
- 各阶段吞吐量。

### 9.3 算法效果

根据算法实际提供：

- 去重命中率。
- 特征匹配率。
- 候选检索命中率。
- 编码成功率。
- 编码接受率。
- 平均编码收益。
- 其他专用指标。

所有比率必须明确分母和分子。

### 9.4 正确性

提供：

- 恢复成功率。
- SHA-256 验证通过率。
- 数据完整性错误数量。

### 9.5 资源开销

提供：

- 峰值内存。
- 平均内存（可测量时）。
- CPU 使用情况。
- 索引内存占用。
- 缓存内存占用。
- 统计模块自身的性能开销。

不得将无法可靠测量的数据作为真实指标输出。

## 十、数据一致性及可复现性要求

1. 每次实验必须具有唯一 experiment_id。
2. 同一实验内 file_id 必须唯一。
3. chunk_id 必须能够关联所属文件。
4. operation_id 必须能够关联对应操作。
5. 所有计时字段统一使用明确的时间单位。
6. 所有字节字段统一使用 Byte。
7. 所有计数器必须明确其统计范围。
8. 不得重复计算同一数据。
9. 不得将不同运行模式的数据混合统计。
10. 不得覆盖历史实验结果。
11. 实验中途失败也应尽可能保留已有统计数据，并标记实验未完成。
12. 必须保存实验配置与代码版本。
13. 导出的汇总结果应能通过明细数据复核。
14. 新增字段应具有版本兼容机制。
15. N/A、0、空值必须具有明确区别。

## 十一、统计开销验证

统计框架本身不能成为新的性能瓶颈。

必须进行以下对照实验：

A：完全关闭统计功能。

B：开启 Benchmark Mode。

C：开启 Profiling Mode。

使用相同的数据集、算法参数、运行环境及输入顺序。

比较：

- 总运行时间。
- 内存峰值。
- CPU 使用情况。
- 输出文件大小。
- 算法结果一致性。

统计开销计算：

`Instrumentation Overhead = (Measured Time - Baseline Time) / Baseline Time`

需要说明不同模式的开销，并评估其是否会影响实验结论。

如果详细统计开销过高，应当优化统计机制，而不是直接忽略其影响。

## 十二、开发约束

1. 不允许修改原有算法的核心逻辑。
2. 不允许改变算法执行顺序。
3. 不允许为了统计数据额外执行算法操作。
4. 不允许统计模块改变 Chunk 生命周期。
5. 不允许统计模块长期持有大块原始数据。
6. 不允许为了方便统计而引入不必要的全局锁。
7. 多线程统计必须保证正确性。
8. 不允许用估算值冒充实际测量值。
9. 不允许使用 0 冒充未执行的操作。
10. 不允许丢失历史实验数据。
11. 不允许仅实现日志打印而不提供结构化导出。
12. 不允许只提供最终汇总而丢失必要的明细数据。

如果发现现有算法本身存在问题，应单独记录，不得在本任务中擅自修复。

## 十三、验收标准

开发完成后，必须满足：

- [ ] 存在独立的通用实验统计模块。
- [ ] 所有现有算法能够接入统一框架。
- [ ] 支持 Benchmark Mode。
- [ ] 支持 Profiling Mode。
- [ ] 支持统一计时和计数。
- [ ] 支持文件级统计。
- [ ] 支持 Chunk 级统计。
- [ ] 支持操作级明细。
- [ ] 支持阶段级统计。
- [ ] 支持算法专用扩展指标。
- [ ] 支持索引和缓存统计。
- [ ] 支持存储空间统计。
- [ ] 支持文件恢复及 SHA-256 校验。
- [ ] 支持多线程统计。
- [ ] 自动导出 CSV 和 JSON / JSONL。
- [ ] 导出文件之间能够正确关联。
- [ ] 重复实验不会覆盖旧数据。
- [ ] 统计模块自身开销经过验证。
- [ ] 开启和关闭统计时，算法输出保持一致。
- [ ] 有完整的字段说明文档。
- [ ] 有新算法接入统计框架的示例。

## 十四、最终交付

完成后提交：

1. 通用实验统计框架的完整源代码。
2. 修改后的原有代码。
3. 统计模块的架构说明。
4. 计时接口与统计接口说明。
5. 完整的数据字段字典。
6. CSV / JSON / JSONL 导出格式说明。
7. Benchmark Mode 和 Profiling Mode 使用说明。
8. 一次 Finesse 实验的完整导出示例。
9. 一次 N-transform 实验的完整导出示例。
10. 一次 FastCDC 实验的完整导出示例。
11. 统计开启和关闭时的性能对照结果。
12. 新算法如何接入该框架的开发指南。

如果现有代码结构无法支持某项要求，必须说明原因、限制及推荐方案，不得通过虚构实现或虚构数据通过验收。

**最终验收标准：一个不了解具体算法实现的研究人员，仅凭实验导出的结构化数据和字段说明，就能够独立分析算法的运行时间、内部行为、资源开销、存储收益和正确性，并能够对不同算法进行公平比较。**

本框架应成为整个仓库长期维护的实验基础设施。后续所有实验均应优先使用该框架，不再单独实现临时计时器和实验数据导出逻辑。
