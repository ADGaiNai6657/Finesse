# 算法与技术规格

[已批准 D-05、D-11] 当前实现目标为 Finesse-Gear 与 NTransform-Gear；Rabin 仅保留在论文依据文档中。两种算法共用固定来源的 GearHash 与 FastCDC 分块输入。

## 术语和参数

`[论文 P-03～P-08]` 输入为一个长度为 L 的字节序列 chunk；feature 是提取的极值，SF 是多个 feature 组合后的哈希。两者均不是用于确认完整内容相等的安全摘要。

| 参数 | 论文实验值 | 含义 |
| --- | --- | --- |
| S | 3 | SF 数量 |
| K | 4 | 每个 SF 的 feature 数量 |
| N | S × K = 12 | feature 总数，也是 Finesse 子块数 |
| 哈希状态 | 64 bits | 来源 GearHash 的无符号状态；不再使用 Rabin 的 48 字节窗口 |

`[已批准 D-10]` 首期使用固定的 12/3/4 配置及定长数组，不提前实现任意维度泛化。各常量只有一处定义，不能在模块中分别硬编码。改变这些值必须生成新配置标识与对应测试。

## N-transform SF

`[论文结构 P-03～P-05；哈希替换已批准 D-05；状态与编码细节见 D-14]`

```text
features[0..N-1] = 0
hash = 0   // 已批准 D-14：每个 chunk 重置
对 chunk 的每个位置 j：
    hash = gearRoll(hash, chunk[j])
    fp = hash
    对 i = 0..N-1：
        value = (m[i] * fp + a[i]) mod 2^32
        features[i] = max(features[i], value)
对 s = 0..S-1：
    superFeatures[s] = GearHash(serialize(features[s*K .. s*K+K-1]))
```

每一组变换参数在所有 chunk 中保持一致。基线按 feature 原始索引连续分组，不使用 Finesse 的排序分组；也不能只对整块最大 Gear 值变换 N 次。

`[已批准 D-07]` 变换运算使用明确的无符号类型，先取 Gear 的低 32 位，再以 64 位无符号中间值完成乘加并取低 32 位；测试包含乘加溢出边界。参数来自版本化文件，记录全部 12 对 `(m_i,a_i)`，不得只记录可能受库版本影响的随机种子。

## Finesse 特征提取

`[论文结构 P-06；哈希替换已批准 D-05]` 将一个 chunk 分成 N 个子块，对每个子块所对应位置的 Gear 值取最大值。算法 2 没有线性变换；不能加入变换来“统一”两种算法。

当 `L % N == 0` 且 `L >= N` 时，子块 i 对应半开区间 `[i*L/N, (i+1)*L/N)`。按已批准 D-14，Gear 状态在子块边界不重置。

`[已批准 D-04]` 非整除长度采用 `begin(i)=floor(i*L/N)`、`end(i)=floor((i+1)*L/N)`，覆盖全部字节，各子块长度最多差 1。实现应避免 `i*L` 的整数溢出。例：`L=14,N=12` 时边界为 `0,1,2,3,4,5,7,8,9,10,11,12,14`。这属于补充规则，不能称为论文明确规定。

`[已批准 D-04]` `L<12` 返回 `UnsupportedLength`，不把零填充的 feature 当作有效签名。正式比较要求两种算法在同一有效输入集合上运行；被排除的 chunk 数量和字节数必须记录。空输入不产生 SF。另一候选方案是支持短块的独立策略，需另批。

## Finesse 分组

`[论文 P-07；编号解释已批准 D-08]` 将 12 个 feature 按原索引分为 **4 个连续集合，每集合 3 个**。每个集合降序排序，再按相同排名跨集合取值：

```text
groups[g] = sort_desc(features[g*S .. g*S+S-1])  // g=0..K-1
sfInput[s] = [groups[0][s], groups[1][s], groups[2][s], groups[3][s]]
superFeatures[s] = GearHash(serialize(sfInput[s]))             // s=0..S-1
```

不要误写成“3 组，每组 4 个，组内哈希”，也不要先对 12 个 feature 全局排序。

图 3 给出的分组向量：

| SF 槽位 | 按集合顺序取出的 feature |
| --- | --- |
| 0，最大 | F1、F5、F7、F9 |
| 1，次大 | F2、F3、F8、F10 |
| 2，最小 | F0、F4、F6、F11 |

`[已批准 D-08]` 相等 feature 采用稳定排序以保留调试时的来源索引；实际哈希只输入值，不输入来源索引。返回的原始 feature 数组保留子块顺序，排序在局部副本中进行。图 3 的最终 SF 十六进制值不适用于 GearHash 变体，只使用其分组向量检验结构。

## GearHash 与 SF 编码

`[已批准 D-05、D-06；已核实来源]` 摘取 FastCDC `be5816e` 的 `GEAR_TABLE[256]` 与 `gearRoll`：`h = ((h << 1) + GEAR_TABLE[byte]) mod 2^64`。保留整张表，不重新随机生成。该函数不移除某个固定窗口的旧字节，因此不能套用 Rabin 的 48 字节窗口或多项式配置。

`[已批准 D-14]` 每个 chunk 从 h=0 开始，按字节更新后取值；Finesse 在子块边界不重置 h，只重置对应 feature 的最大值归约。N-transform 仍按论文执行模 `2^32` 变换，等价于先取 Gear 低 32 位再乘加；Finesse 保留 64 位最大值，不默默把模数升级到 `2^64`。两种算法有效 feature 位宽不同，须在配置与报告中明示。

`[已批准 D-14]` SF 中每个 feature 统一零扩展成 64 位，按小端 8 字节序列化；每个 SF 的 4 个值共 32 字节，从零状态调用 `updateGearHash`，取最后 64 位状态作为 SF。SF 哈希不包含槽号或算法名，以允许 D-09 的跨槽匹配；不同算法和配置仍使用隔离的索引。上述具体值已由 D-14 审批冻结。

CDC 的 Gear 状态与特征提取的 Gear 状态完全独立。CDC 可跳过 MinSize 前缀，特征提取必须扫描 chunk 全部字节；不能把 CDC 最后一个 hash 直接作为 feature 起始状态。

## 相似匹配的边界

`[已批准 D-21]` 输入先经过 SHA-1＋长度/字节确认的精确去重，唯一 payload 进入 ChunkStore。当前 sfInput=unique 仅对首次出现的唯一块提取签名，all 对每次出现从同一池读取；这是提取前的输入选择，不改变以下算法/候选语义。精确重复由内容确认决定，不使用 SF 判断。

`[论文 P-02]` 共享 SF 只是候选条件。SF 不相等不能证明不相似，SF 相等不能证明内容相同。首期没有压缩器，因此不把匹配率等同于节省空间比例。

`[已批准 D-09]` 诊断匹配采用 `sfValue` 键，忽略历史 SF 槽位。当前 chunk 从槽位 0 到 2 查找，任何槽位相同值都可命中；同键保存历史插入最早的 chunk。先查询后插入，不与自身或未来数据匹配。两种算法分别维护索引，禁止跨算法匹配。该选择不是论文完整规定的 FirstFit 实现。

## 复杂度与公平性

`[推导自论文算法]` 若滚动更新为 O(1)，基线 feature 提取为 O(LN)，Finesse 为 O(L)，Finesse 分组为 O(K S log S)，两者 feature 工作空间为 O(N)。固定 N=12 时二者均随 L 线性增长，但常数开销不同。

`[已批准 D-12]` 正式 SF 速度测量必须包含 Gear 扫描、feature 提取、分组和 SF 哈希。预计算 Gear 序列只用于隔离算子测试或正确性检查，不能把其结果标为完整 SF 计算速度。

跨槽示例：A=[11,22,33]，历史 B=[44,55,11]。A.SF0 与 B.SF2 相等，因此命中。若 B 的多个槽相同，只保留一个候选；记录查询槽和历史命中槽便于诊断，历史槽并列时取最小槽号。

N-transform 参数必须使用 [D-15 已批准参数表](07-decisions.md) 的全部 12 对值，不在进程启动时重新随机生成。
